# Pre-split layout experiment — tall rows split before the pagination library

A throwaway measurement harness. It lays out blocks of the shared fixture
series with the pagination library **Paged.js 0.4.3**, in the grid markup,
inside the PDF base image. Before the library starts, an in-page script
**splits every item row taller than a page into continuation parts** that
each fit one page. It also measures how the library lays out long free text.
It decides nothing: it reports what was measured.

The earlier experiments are named by their folders: `spikes/02-pdf-layout`
(the pagination library, its accounting script and the verifier of the end-page
rules) and `spikes/07-native-tall-rows` (the shared fixture series and the
text-integrity checker).

## Hypothesis

In `spikes/02-pdf-layout`, a row taller than a page makes Paged.js 0.4.3 log
`Layout repeated` and silently drop every row after it. The run still
finishes with status ok (the "giant-row signature").

The hypothesis is that if no element reaching the library is taller than a
page, the library never meets that case. The tall row is therefore cut,
before layout, into parts that each fit a page:

- the sequence and date stay on the first part;
- the amount stays on the last part;
- the "(continues)" mark is written by the unchanged accounting script into
  the empty amount cell of every other part.

The block should then print every row and every character. The page
subtotals and the brought-forward / carried-forward chain should stay exact
under the end-page rule, up to the 1 MiB record-size hypothesis. The split
must exist only in the PDF page: the block's semantic HTML must stay unchanged.

## How to run

### Prerequisites

- The local registry `report-service-dev-registry` on `127.0.0.1:5055`, with
  the PDF base image `report-service-pdf-base:1.63.0-10.0.13-noble`, resolved
  to its digest.
- The checker image `text-integrity-check:local`, built from
  `spikes/07-native-tall-rows/Dockerfile.check` (see its README).
- The fixtures, generated by that checker's `fixtures` command and checked
  against `spikes/07-native-tall-rows/results/fixtures.sha256`. This harness
  reads fixture files; it never generates them.
- A quiet engine for the two measured stages: `docker ps` lists nothing but the
  registry, and no other measurement runs at the same time.

### Commands

These run from the product repository root, in PowerShell.
`$wslRoot` is the WSL form of the current directory
(`X:\...\<repository>` becomes `/mnt/x/.../<repository>`). With Docker Desktop
on Windows paths, use `${PWD}` instead of `$wslRoot` in the `-v` arguments.

```powershell

  -f spikes/08-pagedjs-pre-split/Dockerfile -t pagedjs-pre-split-spike:local .

# Check stage 1, then select (not measurements).

```

`run --matrix quick` (6 runs, one stage, default values) is the development
loop and the check that the run records meet the checker's contract. Its
results are not evidence.

### Caps, classes, budget and resume

- **Caps per run:** 300 s inside the run's own process, and the process tree
  is killed at 330 s. The container runs with `--memory 4g --memory-swap 4g`,
  and the cgroup's `oom_kill` counter is read before and after each run.
- **One class per run:**
  - `ok`;
  - `timeout`;
  - `killed-wall-clock`;
  - `oom-killed`;
  - `crashed` — includes a layout the page itself reports as failed, with
    the reason prefixed "the page's layout failed:"; it is a measured
    outcome;
  - `error` — harness defects only;
  - `not-run` — after a cap in a size series, or once the budget is spent.
- **Budget:** 3 h of driver wall clock across both stages. Stage 1 records its
  time, and `select` writes the remaining budget, which stage 2 receives as
  `--budget-seconds`. The time between the stages is not counted.
- **Resume:** `--resume` works within one stage, against that stage's own
  `runs.jsonl`. Re-running stage 1 after `select` voids the selection, so
  `check` and `select` must run again.
- **`scripts`:** the escaping counter written for the checker counts the
  script elements of the laid-out page other than the four this harness
  writes. Rule 8 still compares the scripts found with the four expected.

## The split

The split is chosen inside a fixed choice set, and these are the choices as
applied:

| Axis | As applied | Why |
|------|------------|-----|
| Where it measures | In the PDF page, before the library starts. The copy of the detail goes into an off-screen container of the content width (186 mm), with the same stylesheets; the container is removed before layout. | Same browser, fonts and width as the layout. One navigation. |
| How it cuts | At line boundaries. A binary search on character offsets with `Range` geometry, snapped back to the start of the line that holds the offset, with the half-leading counted. Each part is re-measured. | Every part is a whole number of lines. The fallback (cut by measuring candidate parts over whitespace) was **never needed**: every split row of every run used line boundaries, and no part exceeded its limit. |
| What it cuts | The description cell, and in the five-column geometry also the note cell, each at its own lines. Sequence and date stay on part 1, the amount on the last part, and an empty amount cell is left on the others. Text moves only through text nodes and `textContent`. | The parts concatenate to the original text. The script checks this itself, and it held on every split row. |
| Trigger | **1.00 of the content area.** Selected by the rule from sweep A, case (a): no row of 1.00 or less failed. | Rows that fit a page stay whole. |
| Part limit | **0.90 of the content area.** Selected by the rule from sweep B: all three candidates (0.90, 0.75, 0.50) passed, and the largest is taken. | It leaves room below a full page. |
| Where parts 2…n start | Parts 2…n carry the class `continuation` and get `break-before: page`. Every part has `break-inside: avoid`. | Two fragments of one row on one page would read as a duplicate under rule 1. |
| Marks | Written by the unchanged accounting script of `spikes/02-pdf-layout`. | — |
| Free text | Never split. | Measures the library's own paragraph fragmentation. |
| Reuse | `AccountingVerifier.cs` and `ProcessTreeSampler.cs` are linked and used. `BlockSource.cs`, `LayoutRunner.cs` and `BlockHtmlBuilder.cs` are linked for their types only. `layout.css`, `paged-layout.js` and Paged.js 0.4.3 are linked unchanged. | The end-page rules are unchanged by construction. A new runner, `PreSplitRunner.cs`, calls the pre-split before the layout starts. |

**The semantic source** `semantic.html` and the PDF page `pdf.html` share one
body byte for byte; only the PDF page's `<body>` start tag carries
`data-footer`. On every `ok` run (SEM) three things were checked:

- the semantic file hashes the same before and after the run;
- its body's inner content equals the served PDF page's body content byte
  for byte;
- a fresh, script-free load of the semantic page shows every row once,
  unsplit, with the source text.

### The checker and its controls

The checker of `spikes/07-native-tall-rows` (poppler, no browser) read every
PDF, with its rules TI-1 … TI-8. A control behaves here only when its
expected failure is the **only** failure.

- **Positive controls:** `B100` and `K1` pass TI-1 … TI-8.
- **Negative controls in the page:** each fails with exactly one failure, of
  the expected class at the expected place.
  - On `B100`: `NC-W` `text-dropped` at row 50, `NC-L` `text-repeated` at
    row 50, `NC-R` `row-lost` at row 51.
  - `NC-F` on `F26K-a`: `text-dropped` in the free text after the detail.
  - The same three, inside the split row of `T300u`: each has one failure,
    the expected one.
- **Extraction-level controls E1–E4.** The base is the `G200` split run with
  the footer off, chosen by the fixed rule. E1 `text-dropped`, E2
  `text-repeated`, E3 `row-lost` and E4 `text-altered`, each at row 50, are
  each the **only** failure observed. The checker's own result (any matching
  failure counts) is "yes" for all four.
- **E5–E8 are not evaluable.** The checker's controls cannot take real marks:
  they add simulated marks and evaluate without the footer. That does not make
  the checker untrusted.
- **TI-7 ("continues" marks) rests on the real-mark runs and is not proven
  by a control.** All 45 runs that had the footer on and at least one split
  row pass TI-7, with the marks written by the accounting script. This is an
  observation.

### Printed accounting (PA, `prefix form`)

The checker reports page spans only for rows over two or more pages, so the
exact row set of each page cannot be read from its output. For every run with
the footer on, the prefix form checks three things from the printed footer
and the source amounts in row order:

- brought forward, page subtotal and carried forward chain correctly, and
  the chain closes on the block total;
- every carried forward is the sum of a prefix of the rows;
- every row seen spanning pages is counted on its last page and not before.

It cannot show the exact row set of each page. When ties or zero amounts make
a prefix non-unique, the result is `ambiguous`.

**Results:** 85 `matches`, 3 `differs`, 0 `ambiguous`. The three `differs`
are the expected ones:

- the two lost-row controls (`NC-R`): the chain ends short of the printed
  block total;
- `G200` without the split: the last page has no footer.

Rules 2–3 of the verifier, computed against the page DOM, are reported
beside PA. They pass on every run with the split, and rule 3 fails on `G200`
without the split. On the `NC-R` controls they pass while PA differs: the
verifier builds its block from the rows the page holds, while PA compares
with the printed block total.

## Conclusion

Within what was measured, splitting tall rows at line boundaries into parts
of at most 0.90 of a page, before Paged.js 0.4.3 lays out the grid markup,
removed the silent row loss of `spikes/02-pdf-layout`. In the same harness
and on the same base, the giant-row fixture lost 150 rows without the split
and lost none with it. Every row and every character of rows up to a 1 MiB
record (220 parts, 224 pages) printed, with the page subtotals and the
chain exact under the end-page rule.

The split did not change the ordinary block, and it left the semantic HTML
unchanged. Its own cost ran from about 0.1 s at 1 000 ordinary rows to about
1.1 s for a 1 MiB record. Rows that fit a page (up to 1.00) laid out whole
without a failure. Long free text printed whole up to 1 MiB, but one
1 MiB paragraph took about 33 s to lay out.

These are results for Paged.js 0.4.3, Chromium 153.0.8010.12, this base image

## Maintenance observations

The split depends on these behaviours of Paged.js 0.4.3. They were observed
here, not guaranteed:

- the library honours `break-before: page` and `break-inside: avoid` on the
  grid item rows, so each continuation part starts a new page and is never
  fragmented;
- the accounting script counts fragments by `data-seq` across pages, so the
  parts of one row are one row to the end-page rule;
- the measured height of a part in the off-screen container matches its laid
  out height inside the library's page: no fragment went below the content
  area in any run.

A later library version, other stylesheets or other fonts must be measured
again. The giant-row signature without the split is still present in 0.4.3
on this base.
